# lfsr128sum

Высокопроизводительная C++20 библиотека и консольная утилита для вычисления 128-битных контрольных сумм на базе парных LFSR-генераторов (Linear Feedback Shift Register). Проект сочетает классическую математику регистров сдвига с современными SIMD-инструкциями и защищенной от изменений архитектурой версионирования.

## 🚀 Ключевые особенности

*   **Высокая производительность**: На одном ядре алгоритм обрабатывает **≈7.5 ГБ/с** в ОЗУ (64 МиБ одним вызовом) и **≈6.4 ГБ/с** при хэшировании реального файла 256 МБ (в кэше ОС). Это стало возможным благодаря слитной SIMD-обработке обоих генераторов за один проход, матрицам перехода на блок и двойной буферизации чтения/хэширования (Producer/Consumer).
*   **Встроенное версионирование хэшей**: Вывод утилиты защищен префиксами Modular Crypt Format (например, `$lfsr128$v4$`). Префикс однозначно задаёт версию алгоритма, поэтому хэши разных версий не путаются, а смена внутренних полиномов, солей или масок не ломает формат контрольных сумм.
*   **Умная проверка целостности (`--check`)**: Встроенный валидатор файлов устойчив к Windows-специфике кодировок (автоматически обрабатывает маркеры UTF-8 BOM, срезает невидимые символы возврата каретки `\r` и не зависит от количества пробелов-разделителей).
*   **MAC-режим (keyed-хэш)**: тот же алгоритм с секретным ключом 1..64 байта. Сумму, посчитанную с ключом, нельзя ни проверить, ни подделать без ключа — то есть `--check` защищает уже не только от случайных повреждений, но и от умышленной правки. Стоимость на сообщение — ноль.
*   **Множественная обработка и автономная запись**: Поддерживается передача пачки файлов за один вызов, а флаг `-o` позволяет утилите писать отчет напрямую на диск в обход кодировочных искажений терминалов (вроде UTF-16 LE в PowerShell).
*   **Total Progress Bar**: При обработке множества файлов утилита выводит единую сглаженную шкалу прогресса с динамическим расчетом средней скорости (EMA) и общего времени до окончания (ETA).
*   **Автономная сборка для Windows**: Конфигурация CMake автоматически настраивает статическую линковку библиотек рантайма (`libc++`, `libunwind`), что позволяет исполняемому файлу работать на любой «голой» Windows без предустановленного Qt Creator или компиляторов.

## ⚙️ Как устроен быстрый путь

*   **Слитная SIMD-обработка.** Состояния обоих генераторов (GF(251⁴) и GF(241⁴)) лежат в одном 256-битном регистре: за один блок выполняется 128 тактов, вклады состояния и входов считаются через `_mm256_madd_epi16`, а редукция по модулю — один 32-битный Барретт на блок.
*   **Матрицы перехода O(STEPS).** Вклад блока строится через степени матрицы перехода 4×4, а не прогоном `STEPS` шагов для каждой ячейки и каждого входа.
*   **Корректный вход.** Входные слова приводятся по модулю p до умножения на матрицу; без этого `acc + product` выходил бы за 16 бит и блоковый путь расходился бы со скалярной моделью.
*   **Дешёвые мелкие входы.** Матрицы генераторов зависят только от K1/K2, поэтому копируются из статического прототипа (единицы наносекунд вместо ~1 мкс пересчёта); стартовая соль применяется всегда к единичному состоянию, поэтому её результат тоже предвычислен; при финализации остаются две соли, и возведение в степень идёт сразу для обеих пар одним 256-битным проходом.
*   **Быстрый конвейер чтения.** Штатный `std::counting_semaphore` в llvm-mingw даёт миллисекундные задержки на переключение потока; замена на `mutex + condition_variable` убирает простой.

## 🔖 Версия формата

Хэши имеют префикс **`$lfsr128$v4$`**. Префикс однозначно задаёт версию алгоритма, поэтому смена полиномов, солей или масок не ломает формат контрольных сумм. `--check` сверяет версию и сообщает о неизвестной отдельным сообщением, а не «ложным» повреждением файла.

## 🧬 Как устроен хэш

### 1. Нелинейный слой: почему он обязателен

Вход в LFSR **линеен над GF(p)**: в состояние идёт только `word mod p`, умноженное
на постоянную матрицу перехода. Если убрать нелинейный слой, два разных 16-битных
слова с одинаковым остатком дадут одинаковое состояние, а значит и одинаковый хэш.
Для `p1 = 251` и `p2 = 241` (вторая ветка видит `~word`, что тоже аффинно)
достаточно сдвига

```
Δ = lcm(251, 241) = 60491
```

— и правка одного слова пройдёт «незамеченной» обеими ветками. Сдвиг `±60491`
помещается в 16-битное слово примерно для 15 % значений, но при построении пары
«с нуля» атака детерминирована: ставим в слово `0` и `60491`. Любая линейная схема
(CRC, LFSR) допускает такие конструируемые коллизии — именно поэтому CRC не является
хэшем.

Поэтому к состоянию добавляется **нелинейный ARX-фолд**: четыре 256-битные цепочки,
по одному умножению с переносом на 32 байта; раз в 512 байт цепочки связываются
между собой. Теперь правка данных должна одновременно обнулить и линейный вклад,
и вклад фолда: первое по-прежнему легко, второе — поиск коллизии 128-битного
значения. Стоимость фолда — около 17 % на одном большом вызове, и она окупается
удалением солей из внутреннего цикла.

Финализация — одна 128-битная функция: 16 ячеек состояния (128 бит) и все 128 бит
значения фолда смешиваются пятью раундами ARX с feed-forward, а не двумя
независимыми 64-битными вызовами.

### 2. Один потоковый проход

Файл не режется на блоки и не XOR-ится по блокам: `hasher::update()` дописывает
данные в общее состояние, `hasher::finish()` один раз применяет нелинейное
слагаемое и полную длину. Состояние и длина живут внутри `hasher`, поэтому границы
буферов на результат не влияют, а соль применяется один раз при старте (готовым
прототипом) и дважды при финализации.

`power_by(0)` — тождество (состояние не меняется), а не `x^0 = 1`: соль с нулевым
сдвигом не может схлопнуть состояние в единичное. Это защищает **любой** вызов,
включая «сырой» API `gens`/`add_salt`.

### 3. Потоковый API

```cpp
lfsr_hash::hasher h;                        // доменная соль уже применена
h.update(std::as_bytes(std::span(chunk1))); // куски любого размера
h.update(std::as_bytes(std::span(chunk2)));
lfsr_hash::u128 hash = h.finish();          // 128 бит
```

Результат не зависит от размера кусков: `update` по 1 байту и один вызов на весь
буфер дают одинаковый хэш (это проверяется тестом `streaming == one-shot`).

## 🛡 Алгебраическая архитектура (Multi-Field Mixing)

В отличие от стандартных контрольных сумм (например, CRC32), работающих в одном поле $GF(2^n)$, алгоритм `lfsr128sum` построен на «столкновении» различных алгебраических структур:

1.  **Поле GF(251⁴)**: Арифметика полиномов над простым модулем 251.
2.  **Поле GF(241⁴)**: Арифметика полиномов над простым модулем 241.
3.  **Операция XOR**: Операция линейная для битов, то есть в поле GF(2), но нелинейная в полях GF(251), GF(241).
4.  **Необратимый ARX-миксер (feed-forward)**: Устраняет смещение (bias) в сторону нулевого бита, которое возникает из-за модулей 251 и 241, которые меньше, чем 256.

## 🛡️ Анализ криптографической стойкости

Архитектура системы основана на четырех независимых генераторах состояний, объединенных ARX-миксером. Выбор параметров минимизирует математический резонанс и максимизирует итоговый период хеширования.

### 1. Параметры генераторов
Система использует два простых основания p ≈ 2⁸ и взаимно простые степени $n \in \{3, 4\}$:
*   **Группа A:** $p_1 = 251$, периоды $T_{A1} = 251^4 - 1, T_{A2} = 251^3 - 1$
*   **Группа B:** $p_2 = 241$, периоды $T_{B1} = 241^4 - 1, T_{B2} = 241^3 - 1$

### 2. Математическое обоснование периода
Общий период системы ${T}_{\text{total}}$ вычисляется как наименьшее общее кратное (lcm) всех четырех периодов:

$T = \text{lcm}(\text{lcm}(251^4-1, 251^3-1), ~\text{lcm}(241^4-1, 241^3-1))$

$T \approx 6.86 \times 10^{25} \gtrsim 2^{85.8}$

**Почему это эффективно:**
*   **Взаимная простота степеней (3 и 4):** Поскольку gcd(3, 4) = 1, полиномы x³-1 и x⁴-1 имеют минимальное пересечение — только через общий множитель (x-1). Если бы использовались степени 2 и 4, период сократился бы в x²-1 раз (для 251 это потеря в ≈ 63 000 раз).
*   **Простые основания (241 и 251):** Использование разных простых чисел гарантирует, что специфические множители периодов (такие как 31501 and 29041) не пересекаются, что обеспечивает мультипликативный рост итогового цикла.

### 3. Показатели солей
Соль — это возведение состояния в степень `q` в мультипликативной группе поля. Такое
отображение имеет ядро размера `gcd(q, T)`, и при `gcd > 1` образ сжимается ровно
во столько раз, а вместе с ним падает и эффективное пространство состояний. Поэтому
все показатели выбраны взаимно простыми со всеми четырьмя периодами
(`q = 61, 13, 37`); инвариант закреплён `static_assert` в заголовке и отдельным
тестом.

### 4. Стойкость к коллизиям
Суммарный период генераторов ≈ 2⁸⁵·⁸, а пространство состояний 251⁸·241⁸ ≈ 2¹²⁷. При этом длина сообщения полностью связывается в финализации, а нелинейный фолд убирает конструируемые коллизии, возможные в чисто линейной схеме.

### 5. Границы применимости (важно)

Это **контрольная сумма**, а не криптографический хэш:

*   нет ключа: любой может посчитать значение, поэтому `--check` защищает от случайных повреждений и ошибок хранения, но не от подмены (подпись списка контрольных сумм — отдельная задача);
*   нет опубликованного криптоанализа; уровень стойкости к коллизиям ограничен шириной состояния (≈127 бит, то есть birthday-граница ≈2⁶³·⁵), а не 2¹²⁸;
*   для сценариев с противником используйте SHA-256/BLAKE3 (или HMAC поверх них).

Линейная схема без фолда допускала бы конкретную атаку: правка 16-битного слова на `lcm(251,241) = 60491` не меняла бы хэш. В конструкции с нелинейным слоем она невозможна, и в тестовом наборе есть регрессионный тест `linear injection attack is detected`.

## 🔐 MAC-режим (keyed-хэш)

Обычная контрольная сумма защищает только от случайных повреждений: алгоритм публичный, поэтому, подменив файл, атакующий пересчитает и сумму. MAC-режим закрывает это: тот же хэш, но с секретным ключом 1..64 байта, и без ключа правильный тег не посчитать.

Ключ входит в три места сразу:

| Место | Что делает |
| :--- | :--- |
| Стартовое состояние | ключ проходит тем же линейным движком, что и сообщение, затем применяется доменная соль `S0` |
| Сид нелинейного фолда | нелинейный слой отличается с первого байта, а не только в финализации |
| Слова финализации | XOR до feed-forward, поэтому разность ключа проходит через пять раундов ARX |

Последнее важно: XOR ключа в готовый выход не годится — у схемы линейное ядро, и часть ключа вынеслась бы наружу. Здесь ключ попадает именно в нелинейную часть.

**Стоимость.** Ключевой контекст (`make_key`) считается один раз на ключ — ≈0.67 мкс (80 байт через линейный движок + 12 раундов ARX). На сообщение — ноль:

| Вход | без ключа | с ключом |
| :--- | ---: | ---: |
| 64 Б | 865 нс | 869 нс |
| 4 КиБ | 1 236 нс | 1 239 нс |
| 64 КиБ | 7.80 ГБ/с | 7.67 ГБ/с |
| 8 МиБ | 8.40 ГБ/с | 8.42 ГБ/с |

### API

```cpp
#include "lfsr_hash.h"

std::array<uint8_t, 32> raw = /* ... */;
lfsr_hash::key_ctx k = lfsr_hash::make_key(std::as_bytes(std::span(raw)));

lfsr_hash::u128 tag = lfsr_hash::mac128(k, std::as_bytes(std::span(data)));

// Потоково, с переиспользованием контекста на много файлов:
lfsr_hash::hasher h(k);
h.update(chunk1);
h.update(chunk2);
lfsr_hash::u128 tag2 = h.finish();
```

`make_key` бросает `std::invalid_argument` при пустом ключе или длиннее 64 байт. Ключ дополняется нулями до 64 байт (как в HMAC), а его длина входит в доменную метку, поэтому `"a"` и `"a\0"` — разные ключи.

### Границы применимости

*   **Ключ надо доставить заранее.** Секрет симметричный, поэтому обе стороны должны получить его до проверки: менеджер секретов/конфиг при деплое, TLS- или SSH-канал, либо KDF из общего пароля. MAC эту задачу не решает — он решает «файл не менялся, если секрет уже есть».
*   **Это MAC, а не подпись.** Ключ симметричный: владелец ключа может подделать тег сам, поэтому доказать третьей стороне подлинность файла нельзя. Для этого нужны подписи (Ed25519 и т.п.).
*   **Пароль сюда передавать нельзя.** Ключ дополняется нулями, а не растягивается: `--key` из 8 hex-символов — это 32-битный ключ, а не стойкий пароль. Пароль надо прогнать через KDF (argon2/scrypt) и взять 32 байта.
*   **Домашняя конструкция.** Это не HMAC и не проверенная связка; на стойкость MAC как PRF здесь никто не заявляет, внешнего анализа нет. KAT-векторы фиксируют формат, а не доказывают стойкость.
*   **Формат.** Префикс остался `$lfsr128$v4$`, но суммы с ключом несовместимы с суммами без ключа (и с суммами под другим ключом): проверка просто не сойдётся.

## 🛠 Сборка проекта

Проект самодостаточен и не требует внешних зависимостей. На Windows поддерживается автоматическое развертывание статического рантайма под LLVM-MinGW (Clang) и MSVC.

> **AVX2 не обязателен.** Движок один и тот же (матрицы перехода на 128 тактов, один модуль на блок); меняется только ширина регистров: `__m256i` для AVX2, два `__m128i` для SSE4.2. CMake проверяет поддержку на машине сборки и выбирает реализацию; при отсутствии AVX2 в лог уходит предупреждение, сборка не прерывается, результаты побитно совпадают. Нужен компилятор с C++20: GCC ≥ 11, Clang ≥ 14, MSVC 2019+ (проверено на GCC 11.4 и 13).

```text
-- AVX2: доступен, будет собран слитный блоковый процессор
```

> `-march=native` оптимизирует бинарник под машину **сборки**. Чтобы получить переносимый бинарник (SSE4.2, без AVX2), соберите с `-DLFSR_ARCH_NATIVE=OFF`:
>
> ```bash
> cmake -B build -DCMAKE_BUILD_TYPE=Release -DLFSR_ARCH_NATIVE=OFF
> ```
>
> Такой бинарник проходит тот же набор тестов, включая эталонный хэш, то есть даёт идентичные значения.

```bash
# Клонирование репозитория
git clone https://github.com
cd lfsr128sum

# Конфигурация и сборка в режиме Release (критично для SIMD и многопоточности)
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
```

## 🖥 Использование консольной утилиты

```text
Использование:
  lfsr128sum <файл1> [файл2 ...] [опции]   Вычислить хэш одного или нескольких файлов
  lfsr128sum -c | --check <файл>            Проверить файлы по контрольным суммам

Опции:
  -o, --output <файл>     Записать результат напрямую в чистом UTF-8/ASCII формате
  -k, --key <hex>         MAC-режим: секретный ключ в hex (1..64 байта)
  --key-file <файл|->     MAC-режим: секретный ключ из файла или stdin
  --test                  Запустить тесты корректности, эквивалентности SIMD и покрытия
  --bench                 Запустить бенчмарк производительности алгоритма на ОЗУ
  --version               Вывести версию программы
```

### Примеры команд

*   **Вычисление хэша для одного файла:**
    ```bash
    ./lfsr128sum data.iso
    # Вывод: $lfsr128$v4$87df78aca5d4c320a1116062a4ea3997  data.iso
    ```

*   **Генерация файла контрольных сумм для группы файлов напрямую на диск:**
    ```bash
    ./lfsr128sum main.cpp lfsr_hash.h CMakeLists.txt -o checksums.lfsr
    ```

*   **Проверка целостности файлов по проверочному списку:**
    ```bash
    ./lfsr128sum --check checksums.lfsr
    ```

*   **MAC-режим: контрольные суммы с секретным ключом:**
    ```bash
    ./lfsr128sum backup.tar --key 00112233445566778899aabbccddeeff -o sums.mac
    ./lfsr128sum --check sums.mac --key 00112233445566778899aabbccddeeff
    ```
    Без ключа (или с другим ключом) проверка честно сообщит об ошибке: подделать список сумм, не зная ключа, больше нельзя.

*   **Ключ из пайпа/файла — так, чтобы он не попал в `ps` и историю shell:**
    ```bash
    head -c 32 /dev/urandom > key.bin && chmod 600 key.bin
    ./lfsr128sum backup.tar --key-file key.bin -o sums.mac
    ./lfsr128sum --check sums.mac --key-file - < key.bin    # ключ через stdin
    ```
    `--key-file -` читает stdin, поэтому годится и менеджер секретов: `vault kv get -field=key secret/hash | ./lfsr128sum backup.tar --key-file -`.
    Ключ из stdin/файла — **сырые байты, а не hex**: hex-строку надо распаковать (`printf 'deadbeef' | xxd -r -p`). Один завершающий перевод строки (LF или CRLF) отбрасывается, так что подойдёт и просто `echo secret > key.bin`; если ключ действительно кончается байтом `0x0A`, добавьте лишний перевод строки. Ключ из терминала не читается (`-` при подключённом tty — ошибка): для ручного ввода есть `--key <hex>`.

## 📦 Использование как C++ библиотеки

### 📥 Поточное хэширование (Streaming Mode)

Библиотека поддерживает **поточное хэширование** (Streaming Mode), что позволяет обрабатывать данные кусками любого объема, сохраняя внутреннюю цепочечную зависимость состояний регистров.

```cpp
#include "lfsr_hash.h"
#include "lfsr_file_hash.h"
#include "progress_bar.h"

// 1. Прямой расчет хэша файла.
//    calculate_file_hash128(const fs::path&, ProgressBar&, uint64_t overall_offset)
ProgressBar bar(fs::file_size("data.bin"), "data.bin");
lfsr_hash::u128 file_hash = lfsr_file_hash::calculate_file_hash128("data.bin", bar, 0);

// 2. Расчет хэша с привязкой к общему ProgressBar
ProgressBar total_bar(1024 * 1024 * 100, "Processing Package");
lfsr_hash::u128 chunk_hash = lfsr_file_hash::calculate_file_hash128("chunk1.bin", total_bar, 0);

// 3. Низкоуровневое потоковое хэширование в памяти
lfsr_hash::hasher hasher;                     // доменная соль уже применена
for (auto& memory_chunk : chunks) {           // memory_chunk: std::span<const std::byte>
    // Состояние (LFSR + нелинейный фолд + длина) сохраняется между вызовами
    hasher.update(memory_chunk);
}
lfsr_hash::u128 final_hash = hasher.finish(); // полная длина + финализация

// 4. Математический откат состояния генератора назад (для реверс-инжиниринга)
lfsr_hash::gens gen;   // «сырой» генератор, по-прежнему доступен
gen.g_251x4.back_simd_block(last_processed_simd_block);
```
